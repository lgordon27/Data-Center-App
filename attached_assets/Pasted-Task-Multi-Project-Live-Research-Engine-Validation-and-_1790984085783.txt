Task: Multi-Project Live Research Engine Validation and Root-Cause Repair

This is the highest-priority SafeLoc task.

The core product is the research engine:
selected project → discovery → source acquisition → passage extraction → structured claims → identity/scope validation → eligibility → diligence category output → reviewable evidence.

The current failure mode is unacceptable: SafeLoc can retrieve dozens of source records and still produce zero eligible findings.

Task #351 improved request idempotency, source ranking, source-family diversity, blocked-receipt reuse, and run-yield metrics. This task must now determine whether the live engine actually works across multiple arbitrary projects and, if it does not, isolate the exact systemic conversion bottleneck and repair it.

This is not a UI-polish task.
This is not a backtest.
This is not a historical-reconstruction exercise.
This is not a one-project special case.

Treat this as a production-engine validation and repair exercise.

==================================================
PRIMARY OBJECTIVE
==================================================

Determine whether SafeLoc can reliably convert real public evidence into eligible findings across multiple arbitrary data-center projects.

Run a controlled live matrix across 3 materially different non-canonical projects.

For each project, follow the full real production path:

project selection
→ live discovery
→ candidate ranking
→ document opening
→ extraction
→ passage compaction
→ category analysis
→ structured claim generation
→ project identity/scope validation
→ source validation
→ eligibility
→ diligence output
→ reviewable evidence

The key success metric is NOT source count.

The key success metric is:

credible public project evidence → attributable, scope-correct eligible findings.

==================================================
ROOT-CAUSE ANALYSIS
==================================================

After all 3 runs, do NOT merely summarize the projects.

Build a cross-project funnel showing where evidence is being lost.

Example:

Across 3 projects:
120 unique candidates
→ 55 opened
→ 31 usable sources
→ 84 unique passages
→ 46 structured claims
→ 29 identity-valid
→ 21 scope-valid
→ 7 eligible findings

The purpose is to identify the dominant systemic loss point.

Rank the top 3 engine bottlenecks by evidence impact.

Possible examples:
- discovery fails to surface authoritative sources
- ranking still overweights secondary pages
- exact-project identity rejects valid aliases
- passage extraction strips necessary facility context
- structured analysis fails to produce claims from valid text
- scope logic is overly brittle
- source metadata is lost between extraction and eligibility
- category analysis times out before claims are produced
- valid claims are rejected by formatting/normalization bugs

Do not speculate.

Every claimed bottleneck must be supported by captured run evidence.

==================================================
IMPORTANT: ELIGIBILITY MUST REMAIN STRICT
==================================================

The goal is not to manufacture eligible findings.

A run with zero findings can be correct if public evidence is genuinely insufficient.

But a run is NOT acceptable if:
- SafeLoc opens strong project-specific sources;
- extracts relevant passages;
- and then loses those facts because of internal parsing, attribution, scope, timeout, or normalization failures.

The task must distinguish:
“no public evidence exists”
from
“SafeLoc failed to convert available evidence.”

==================================================
SUCCESS CRITERIA
==================================================

This task is a PASS only if the result demonstrates one of the following:

A. The engine now produces meaningful eligible findings across multiple arbitrary projects when qualifying evidence exists;

OR

B. For any project producing zero eligible findings, the audit proves that the failure is due to genuine evidence insufficiency or inaccessible sources rather than an internal conversion defect.

Preferred evidence of engine health:

- more than one project produces eligible findings;
- eligible evidence comes from more than one source family;
- authoritative/project-specific sources are represented;
- valid passages survive through identity/scope/eligibility;
- category analysis completes for the highest-value categories;
- open-budget waste is materially reduced;
- one click reliably creates one run.

Do not define success by:
- candidate count
- source-record count
- passage count
- UI rendering alone

==================================================
FAIL CONDITIONS
==================================================

Treat any of these as a core-engine failure:

- one click creates multiple unexplained live runs
- official/project-specific sources are discovered but consistently not opened
- 24 opens are exhausted primarily on duplicates/generic/weak sources
- strong exact-project passages are extracted but never become structured claims
- structured claims repeatedly lose source/scope metadata
- valid claims are rejected because of normalization defects
- category analysis routinely times out before using available evidence
- canonical facts leak into arbitrary-project evidence
- zero eligible findings across all 3 projects despite clearly available qualifying public evidence
- blocked/failed searches are shown as conclusive no-evidence outcomes
